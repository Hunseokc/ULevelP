# 01. 기획

## 1. 배경

ULeveLP는 기타 연습용 웹 앱입니다. 지금은 만든 사람 한 명이 쓰고 있고, 기능은 세 가지입니다.

1. **코드 연습실** (`chords.html`): 스케일, 코드톤, 보이싱, 탑노트, 재해석, 2-5-1. 서버 없이 브라우저에서 계산합니다.
2. **연습 플레이어** (`practice.html`): 유튜브 구간 반복, 속도 조절, 녹음. 위치·구간·속도, 하루 연습 시간, 녹음을 **노션**에 저장합니다.
3. **학습 노트** (`notes.html`): 유튜브 링크와 태그를 넣으면 **Gemini**가 영상을 분석해 노션 페이지를 만듭니다.

데이터 저장과 기록 열람은 전부 노션이 맡고 있습니다. 노션 API는 브라우저에서 직접 부를 수 없어서(CORS 미지원) Google Apps Script 중계 서버를 거칩니다. 학습 노트는 GitHub Actions에서 실행됩니다.

## 2. 문제

다른 사람이 쓰려면 아래를 전부 해야 합니다. 개발자가 아니면 따라 하기 어렵습니다.

- 노션 통합 만들기, DB 3개를 정확한 속성 이름으로 만들고 연결
- Apps Script를 웹 앱으로 배포하고 비밀 키 설정
- 저장소 Fork, Actions 켜기, 시크릿 등록, GitHub 토큰 발급, Gemini 키 발급

## 3. 목표

- **G1. 가입만 하면 바로 쓴다.** 구글 계정으로 로그인하면 플레이어, 연습 기록, 녹음을 설정 없이 쓸 수 있다. GitHub 관련 설정은 일반 사용자에게 하나도 요구하지 않는다.
- **G2. 기록을 앱 안에서 본다.** 노션이 해 주던 기록 열람(연습 기록, 곡 목록, 녹음 듣기)을 앱 화면으로 만든다.
- **G3. 노션과의 연결은 유지한다.** 지금 쓰는 노션 페이지 구조를 **공식 템플릿(데이터의 틀)**으로 삼는다. 서비스 데이터를 노션으로 내보내고, 노션 데이터를 서비스로 가져올 수 있다.
- **G4. 키를 넣으면 지금 기능을 전부 그대로 쓴다.** 노션 키를 등록한 사용자는 서비스와 노션이 실시간으로 연동된 상태로 쓰고, Gemini 키를 등록한 사용자는 학습 노트를 쓴다. 소유자(만든 사람)도 같은 경로로 쓴다. 비용은 각자 키로 나간다.
- **G5. 녹음 용량 부담은 각자에게.** 녹음 파일은 최종적으로 사용자 본인의 구글 드라이브에 저장한다.

## 4. 하지 않는 것

- 서비스 비용으로 Gemini 분석 제공 (각자 등록한 키로만 분석. 운영자 키를 다른 사용자에게 빌려주지 않음)
- 노션과 서비스의 완전한 양방향 실시간 동기화 (실시간 연동도 서비스가 원본이고, 노션에서 바뀐 일부 항목만 가져옴. [03-design.md 6.4](03-design.md#64-노션-실시간-연동))
- 범용 노션 프록시 (Edge Function마다 하는 일이 정해져 있음)
- 팀·공유 기능 (기록은 사용자 한 명의 것)
- 유튜브 오디오 내려받기 (약관 문제)
- 네이티브 앱. 웹 앱(PWA)으로 아이패드 홈 화면에 추가해서 씀

## 5. 사용자

| 역할 | 누구 | 쓸 수 있는 것 |
| --- | --- | --- |
| 비로그인 | 처음 온 사람 | 코드 연습실 전체, 플레이어(기록은 그 기기 브라우저에만) |
| 사용자 `user` | 구글로 로그인한 사람 | 위 + 곡·연습 기록·녹음 저장, 기록 화면, 노션 내보내기·가져오기, 구글 드라이브 연결 |
| 노션 키 등록 | SETTING에 자기 노션 키를 넣은 사용자 | 위 + 노션 실시간 연동 |
| Gemini 키 등록 | SETTING에 자기 Gemini 키를 넣은 사용자 | 위 + 학습 노트 |
| 소유자 `owner` | 만든 사람 (지정된 계정) | 기능은 사용자와 같음. 운영 값(녹음 한도 `take_quota_bytes` 상향 등)만 다름 |

키 등록은 사용자가 화면에서 하고, 등록 여부로 기능이 열립니다(D13·D15). 소유자 표시와 운영 값은 DB에서 직접 바꿉니다(`profiles.role`, `take_quota_bytes`). 화면에서 바꿀 수 없습니다.

## 6. 결정 사항

| ID | 결정 | 이유 | 상태 |
| --- | --- | --- | --- |
| D1 | 백엔드는 **Supabase**(Auth, Postgres, Storage, Edge Functions). 화면은 지금처럼 **GitHub Pages** 정적 호스팅 | Supabase는 브라우저에서 바로 호출되고(CORS) 로그인·권한을 맡아 줌. 중계 서버를 따로 운영할 필요가 없음 | 확정 |
| D2 | 로그인은 **Supabase Auth + Google OAuth**만 | 보안을 OAuth에 맡김. 구글 드라이브 연결과 같은 계정 | 확정 |
| D3 | 테이블은 **지금 노션 DB 구조를 그대로** 옮기고 `user_id`로 묶음. 접근 제어는 RLS(`user_id = auth.uid()`) | 노션 템플릿과 1:1로 대응해야 내보내기·가져오기가 단순해짐 | 확정 |
| D4 | 노션은 **템플릿 + 내보내기/가져오기(모든 사용자)**, **실시간 연동(노션 키를 등록한 사용자)** | 노션을 걷어내면 기록 열람·저장을 다 새로 만들어야 하고, 노션을 필수로 하면 설정이 무거움. 둘 사이의 절충. 실시간 연동은 키만 넣으면 누구나(D15) | 확정 (R2 개정) |
| D5 | Gemini 학습 노트는 **Gemini 키를 등록한 사용자**. 키는 화면에서 입력받아 서버(Supabase Vault)에 보관하고, 비용은 각자 키로 나감 | 운영자 키를 빌려주지 않으니 비용·남용 문제가 운영자에게 오지 않음. Edge Function 실행량만 요청 제한으로 묶음(NFR-OPS-5) | 확정 (R2 개정, D13) |
| D6 | 녹음은 최종적으로 **사용자 구글 드라이브**(`drive.file` 권한) | 저장 비용을 사용자에게 넘김 | 확정 |
| D7 | 녹음 저장소는 **단계적으로**: 먼저 Supabase Storage(사용자별 한도), 나중에 드라이브 | 드라이브 토큰은 1시간이면 만료되고 갱신 처리가 필요해서, 화면·데이터를 먼저 안정시킨 뒤 붙이는 게 위험이 적음 | 추천안. 확정 전 |
| D8 | 운영용 Docker 서버는 두지 않음. Docker는 로컬 개발용으로만 유지 | Supabase + 정적 호스팅이면 서버가 필요 없음. 사용자에게 Docker를 요구하면 설정 부담이 다시 생김 | 추천안. 확정 전 |
| D9 | 프런트엔드는 지금처럼 **빌드 도구 없는 바닐라 JS**. 라이브러리는 정확한 버전을 고정해 CDN에서 불러옴 | 지금 코드와 같은 방식. 배포가 단순함 | 확정 |
| D10 | 로그인하지 않아도 플레이어는 지금처럼 동작(기기 저장). 처음 로그인할 때 이 기기의 기록을 계정으로 옮길지 물어봄 | 첫 경험을 막지 않음 | 확정 |

검토했다가 버린 방안:
- **노션 걷어내고 브라우저 저장소(IndexedDB)만 쓰기**: 기기 간 동기화와 백업을 따로 만들어야 해서 오히려 무거움.
- **공용 노션 중계 서버(Cloudflare Worker)를 직접 운영하고 사용자는 노션 토큰만 입력**: 남의 노션 토큰이 내 서버를 거쳐 가고, 노션이 여전히 필수라 설정 부담이 남음.
- **사용자마다 Docker로 띄우기**: 설정 부담이 지금과 비슷함.

각 단계는 앞 단계가 끝나야 시작합니다. 단계마다 [02-requirements.md](02-requirements.md)의 해당 요구사항 인수 조건을 통과해야 끝난 것으로 봅니다.

| 단계 | 내용 | 요구사항 | 끝나면 |
| --- | --- | --- | --- |
| P0 | Supabase 프로젝트, 구글 로그인, 테이블·RLS·함수, RLS 테스트 | FR-AUTH, NFR-SEC | 로그인·로그아웃 되고, 다른 사람 데이터는 못 읽음이 테스트로 확인됨 |
| P1 | 플레이어 저장 계층을 Supabase로 교체, 녹음을 Supabase Storage에 저장, 비로그인 기기 기록 옮기기 | FR-SONG, FR-SESSION, FR-TAKE, FR-LOCAL | 플레이어가 노션 없이 로그인만으로 저장됨 |
| P2 | 기록 화면(LOG), 곡 목록·상세, 녹음 듣기·비교, 첫 화면 PLAYER 프레임 교체 | FR-LOG, FR-LIB | 노션을 열지 않아도 기록을 다 볼 수 있음 |

| P4 | 키 등록(Vault), 노션 실시간 연동(보내기·가져오기), 소유자의 기존 노션 데이터 이전, Apps Script 중계 서버 폐기 | FR-KEY, FR-SYNC | 노션 키를 등록한 사용자는 서비스에서 연습하면 노션에도 쌓임 |
| P5 | Gemini 학습 노트를 Edge Function으로, 노트 화면, GitHub Actions 분석 폐기 | FR-NOTE | Gemini 키를 등록한 사용자가 노트를 만들 수 있고, 키가 없으면 버튼이 비활성 |
| P6 | 녹음을 구글 드라이브에 저장 (선택해서 켜기), 기존 녹음 옮기기 | FR-DRIVE | 드라이브를 연결한 사용자의 새 녹음은 드라이브에 저장됨 |
| 상시 | 디자인 규칙(DESIGN.md), 접근성, 아이패드 확인 | NFR | |

P0 전에 [03-design.md 10장](03-design.md#10-먼저-확인할-것-스파이크)의 확인 작업 S1~S4를 먼저 해 두면 뒤 단계에서 설계를 바꿀 일이 줄어듭니다.

## 8. 위험

| 위험 | 대응 |
| --- | --- |
| RLS 정책 실수로 다른 사용자 데이터 노출 | 모든 테이블에 정책 테스트(P0 필수). 클라이언트에는 공개 키(anon)만 둠 |
| Supabase 무료 플랜은 7일 동안 요청이 없으면 일시정지 | 사용자가 늘면 Pro 플랜. 그 전에는 대시보드에서 다시 켬 |
| Supabase Storage 무료 1GB | 사용자별 녹음 한도(기본 200MB), P6에서 드라이브로 분산 |
| Gemini 영상 분석이 Edge Function 실행 시간 한도를 넘음 | S1에서 측정. 넘으면 구간 나눠 분석 → 길이 제한 → GitHub Actions(실행 중 Vault에서 그 사용자 키를 꺼냄) 순서로 ([03-design.md 7.1](03-design.md#71-실행)). 사용자 키는 저장소 시크릿에 둘 수 없음 |
| 다른 사용자의 키를 보관함 | Vault 암호화, 저장은 본인 RPC로만, 원문 조회는 service role만, 해제·계정 삭제 시 Vault에서 지움. 권한 회수를 pgTAP로 확인(NFR-SEC-8) |
| 키 등록 사용자가 늘면 Edge Function 실행량(운영 비용)이 늘어남 | 학습 노트 요청 제한, 노션 가져오기 5분 간격(NFR-OPS-5). 노션 보내기는 한 실행에서 시간 한도 안에서만 돌고 다음 실행에 이어 감 |
| 같은 Origin(`hunseokc.github.io`)의 XSS로 로그인 세션을 빼앗김 | 키는 브라우저에 없으니 세션으로 할 수 있는 일만 가능(로그아웃·세션 폐기로 막힘). XSS 자체를 막음(D20, X1·X2). 도메인이 생기면 주소 분리(D21) |
| 구글 OAuth 앱 검증 | 검증 전에는 테스트 사용자(최대 100명)만. 공개 전에 동의 화면 검증 신청 |
| 노션 CSV 병합에서 관계형(곡↔연습 기록) 연결이 안 될 수 있음 | S2에서 확인. 안 되면 문서화된 대체 방식 사용 ([03-design.md 6.2](03-design.md#62-내보내기-서비스--노션-fr-nx-2)) |
| 노션 DB에 다른 프로그램(크롬 확장 프로그램)도 쓰고 있음 | 실시간 연동의 가져오기가 노션에서 새로 생긴 곡을 받아들이도록 설계 |
