# 시니어(상위 AI) ↔ 주니어(저수준 AI) 협업 방식

구현하는 쪽(주니어)이 판단할 일을 최소로 줄이는 방식이다. 판단은 명세를 쓰는 쪽(시니어)이 미리 끝내 둔다.
세밀한 명세는 개발 중에 쉽게 틀어지므로 **바로 다음 묶음에만** 쓰고, 앞 묶음의 실제 결과를 보고 다음 명세를 쓴다.
리뷰에서 지적받은 내용은 [주니어_체크리스트.md](주니어_체크리스트.md)에 쌓아 두고, 주니어가 작은 판단을 할 때 기준으로 쓴다.

## 1. 역할

| 역할 | 누가 | 하는 일 | 하지 않는 일 |
| --- | --- | --- | --- |
| **사용자** | 사람 | 메뉴얼 항목 결정, 승인, **머지** | — |
| **시니어** | 상위 AI (effort 높음) | 전체 설계(`docs/01~04`), 묶음 명세(`?0` step), 앞 묶음 검토, PR 리뷰 코멘트 | 구현 step의 코드 작성, 머지 |
| **주니어** | 저수준 AI (effort 중간) | 명세대로 구현, 테스트 실행, 결과 파일, PR, 리뷰 반영, 체크리스트 추가 | 설계 결정, 명세 밖 변경, 다음 묶음 시작, 머지 |

**역할 판별:** 세션 시작 지시에 나온 작업으로 정한다.
- `?0` 명세 step(A0, B0 …), "PR #n 리뷰", 설계 문서 수정 → **시니어**
- 그 밖의 구현 step(K1-1 등)과 "리뷰 반영" → **주니어**

## 2. 설계를 두 층으로 나눈다

| 층 | 문서 | 세밀도 | 언제 쓰나 |
| --- | --- | --- | --- |
| 전체 설계 | `docs/01~04`, 진행 파일 단계 표 | 보통 수준. 결정·경계·DDL·핵심 SQL만 세밀하게 | 처음 한 번. 이후 묶음 검토에서 고친다 |
| 구현 명세 | `개발산출물/명세/<step ID>_구현명세.md` | 그대로 옮겨 치면 될 정도 | **바로 다음 묶음만**, 앞 묶음 결과를 본 뒤 |

먼 step까지 미리 세밀하게 쓰지 않는다. 앞 step 결과(DTO 이름, 서비스 구조, 테스트 도구)에 따라 달라지므로 다시 쓰게 된다.

## 3. 반복 주기

```
[시니어] 묶음 X 명세(X0): 앞 묶음 코드·결과 검토 → step별 구현 명세 작성 → PR → (사용자 머지)
   ↓
[주니어] step 1: 명세·체크리스트 읽기 → 구현 → 테스트 → 결과 파일 → PR
[시니어] PR 리뷰 → PR 코멘트
[주니어] 리뷰 반영 커밋 + 체크리스트 추가 → CI 통과 → (사용자 머지)
   ↓  … 묶음 안의 step마다 반복 …
[주니어] 마지막 step 머지 대기 시: "X 묶음(…) 단계 완료하였습니다. 다음 진행은 문서 보강 및 검토 후 진행이 필요합니다." → 정지
   ↓
[시니어] 다음 묶음 명세(Y0) …
```

- 묶음 구성과 관문 규칙은 진행 파일(예: [진행_코틀린서버.md](진행_코틀린서버.md) 3.1절)에 적는다.
- 묶음 크기는 step 3~4개다. 너무 크면 명세가 틀어지고, 너무 작으면 시니어 세션이 낭비된다.

## 4. 시니어: 구현 명세 작성 규칙

### 4.1 필수 항목 (step마다)
1. **파일 목록**: 경로, 신규/수정 여부, 파일마다 하는 일 한 줄. 목록에 없는 파일은 고치지 않는다.
2. **시그니처**: 클래스, 함수(인자·반환 타입), 라우트 등록 위치. 기존 패턴 파일을 "이 파일처럼"으로 지정한다.
3. **DTO 필드 표**: 이름, 타입, null 허용, 기본값, DB 컬럼, 예시 값. 요청과 응답을 따로 적는다.
4. **검증·에러 표**: 조건 → `status` / `code` / `message`. 정상 응답의 상태 코드는 하나로만 적는다.
5. **처리 순서**: 번호 매긴 단계, 트랜잭션 시작·끝, 실행할 SQL(또는 04 절 번호), 외부 호출이 트랜잭션 밖인지 여부.
6. **테스트 케이스 표**: 이름 / 준비 데이터 / 요청 / 기대 결과. 실패 케이스(잘못된 입력, 남의 데이터, 경계값)를 포함한다.
7. **체크리스트**: `[ ]` 항목마다 확인 명령과 기대 출력. 이것을 다 채우면 완료다.
8. **금지 사항**: 이 step에서 특히 하기 쉬운 잘못(5절에서 골라 적는다).

### 4.2 이렇게 쓰면 주니어가 헤맨다 (금지)
- 응답을 `{ "song": { ... } }`처럼 생략한다 → 필드를 모두 적는다.
- `200 OK / 201 Created`처럼 둘을 함께 적는다 → 조건별로 하나씩 적는다.
- 검증 범위가 없다 → 길이, 범위(예: `rate` 0.25~2.0), 허용 값, 형식(정규식)을 적는다.
- 엔드포인트별 에러 코드가 없다 → 4.1의 4번 표로 적는다.
- 파일 위치나 클래스 이름을 맡긴다 → 경로와 이름을 정해 준다.
- "정확성 테스트 통과"처럼 기준이 모호하다 → 입력과 기대 출력을 적는다.
- 화면에 정상 상태만 있다 → 빈/로딩/에러/비로그인 상태, DOM 구조, 이벤트를 적는다.
- 숫자의 단위가 없다 → 초/분, 바이트/MB, UTC/로컬 날짜를 적는다.
- "적절히", "필요하면", "등" → 쓰지 않는다. 고를 일이 있으면 시니어가 고른다.

### 4.3 앞 묶음 검토 (X0 step 첫 작업)
- 앞 묶음 명세와 실제 코드를 비교하고, 결과 파일의 "명세와 달라진 점"을 확인한다.
- 다음 묶음이 따를 실제 패턴(파일, 이름, 헬퍼)을 명세에 그대로 인용한다.
- 체크리스트에 새로 쌓인 항목 중 설계 문제인 것은 `docs/`에 반영한다.
- 결과는 `결과/<묶음>0_명세검토.md`에 적는다. 새로 정한 메뉴얼 항목(API 필드, 시그니처, 경로)은 사용자 확인을 받고 기록한다.

## 5. AI가 저지르기 쉬운 잘못 (명세 금지 사항과 리뷰의 기준)

| 잘못 | 막는 방법 |
| --- | --- |
| 스펙에 없는 필드, 파라미터, 엔드포인트를 지어낸다 | DTO 표에 없는 필드는 추가 금지 |
| 함수 시그니처, export 이름, 파일 경로를 임의로 바꾼다 | 메뉴얼 항목이다. 바꾸려면 멈추고 묻는다 |
| 요청 범위 밖 리팩터링, 다른 파일 수정, 포맷 일괄 변경 | 파일 목록 밖은 손대지 않는다 |
| 실패하는 테스트를 단언 완화, `@Disabled`, 항상 참인 조건으로 통과시킨다 | 테스트를 고칠 때는 이유를 결과 파일에 적는다. 리뷰에서 diff를 확인한다 |
| 실행하지 않은 결과를 "통과", "완료"로 쓴다 | 명령 출력 끝 몇 줄을 결과 파일에 붙인다 |
| 예외를 삼키고 `null`이나 빈 값을 돌려준다 | 에러 표대로 응답한다. 빈 `catch` 금지 |
| 라이브러리 버전, API 메서드 이름을 추측한다 | 기존 `build.gradle.kts`·코드에서 확인한다. 새 라이브러리 추가 금지 |
| 하드코딩(URL, 키, 사용자 ID)을 쓴다 | 설정(`config`·env)에서 읽는다 |
| 목(mock)을 과하게 써서 실제 SQL을 검증하지 않는다 | DB 로직은 테스트 컨테이너 DB로 검증한다 |
| 다른 사용자 데이터 접근을 검증하지 않는다 | 사용자 A·B 교차 테스트를 넣는다 |
| 명세와 다르게 구현하고 말하지 않는다 | "명세와 달라진 점"에 적거나 멈추고 묻는다 |
| 작업과 무관한 파일(개인 메모, 백업)을 커밋한다 | `git status`로 확인하고 목록 밖 파일은 커밋하지 않는다 |
| 다음 step, 다음 묶음까지 이어서 진행한다 | 관문 규칙. 한 세션에는 한 step만 한다 |

## 6. 주니어 행동 규칙

1. 시작할 때 진행 파일, 해당 step 명세, [주니어_체크리스트.md](주니어_체크리스트.md)를 읽는다. 명세가 없으면 코드를 쓰지 않고 멈춘다.
2. 판단이 필요하면 다음 순서로 찾는다: **명세 → 체크리스트 → 명세가 "이 파일처럼"으로 지정한 기존 코드**. 셋 다 답이 없으면 멈추고 묻는다(문제 보고 형식).
   - 스스로 정해도 되는 것: CLAUDE.md "자유" 항목(내부 변수명, 문구, UI 배치)
   - 정하면 안 되는 것: "메뉴얼" 항목(스키마, API 필드, 시그니처, export, 경로)
3. 명세 체크리스트를 모두 `[x]`로 채우고 확인 명령 출력을 결과 파일에 붙인 뒤 PR을 올린다.
4. PR을 올리기 전에 체크리스트의 모든 항목으로 diff를 스스로 점검하고, PR 본문에 "체크리스트 점검 완료"를 적는다.
5. 명세와 다르게 구현했다면 결과 파일 "명세와 달라진 점"에 이유와 함께 적는다.

## 7. PR 리뷰 루프

1. **주니어:** PR을 올리고 CI를 기다린다(`gh pr checks --watch`). CI가 통과하면 "PR #n — 시니어 리뷰 대기"로 알린다.
2. **시니어:** 명세, 5절 표, 체크리스트를 기준으로 리뷰하고 **PR 코멘트**로 남긴다.
   - 형식: 번호, `파일:줄`, 문제, 고칠 방향. "머지 전 수정"과 "다음 단계로 미뤄도 됨"으로 나눈다.
3. **주니어:** 반영 커밋 `fix(scope): <step> 리뷰 n·m번 반영`을 올린다. 반영하지 않은 번호는 이유를 PR 코멘트로 단다.
4. **주니어:** 지적 하나마다 **일반화한 규칙**을 체크리스트에 추가한다(형식은 체크리스트 파일 머리말). 같은 종류의 지적이 이미 있으면 새로 쓰지 않고 그 항목을 `중요`로 올린다.
5. **사용자:** 머지한다. AI는 `gh pr merge`를 하지 않는다.

## 8. 관문 문구

| 상황 | 주니어가 쓰는 문구 |
| --- | --- |
| step 명세 파일이 없음 | `<step ID> 구현 명세가 없습니다. 다음 진행은 문서 보강 및 검토 후 진행이 필요합니다.` |
| 묶음 마지막 step 완료 | `<묶음> 묶음(<step 목록>) 단계 완료하였습니다. 다음 진행은 문서 보강 및 검토 후 진행이 필요합니다.` |
| 명세로 판단할 수 없음 | 문제 한 줄 → 원인 → 추천 1개(+대안) → "진행할까요?" |
