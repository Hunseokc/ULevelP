# 키 보관·중계 가이드 요약 (ULevelP 적용판)

원문: 사용자가 준 「GitHub Pages + Supabase + Apps Script로 만드는 노션 기반 앱 유저·키 관리 가이드(GAS cashing)」(2026-10-29, @더덕).
원문은 로그인(이메일·비밀번호)과 GAS 중계까지 다루지만, 여기에는 **사용자별 API 키를 서버에 보관하고 중계 서버가 대신 쓰는 부분**만 옮겼다. ULevelP는 로그인을 Google OAuth로 하고(D2), 중계를 Edge Function으로 한다(D16).

## 1. 원칙

1. **키는 브라우저에 두지 않는다.** `hunseokc.github.io` 아래 모든 저장소(guitar-practice, ULevelP …)는 Origin이 같아서 localStorage를 공유한다. 앱 하나의 XSS가 전부의 값을 읽는다. 키는 Vault에만 있고, 서버(Edge Function)만 꺼낸다.
2. 세션 토큰도 같은 localStorage에 있지만(refresh token 포함), 키를 서버에 두면 탈취된 세션으로는 **허용된 동작만** 할 수 있고 **로그아웃·세션 폐기로 바로 막힌다.** 키는 사용자가 재발급하기 전까지 계속 유효하므로 훨씬 위험하다.
3. anon(publishable) 키는 공개된다고 보고, 보호는 RLS가 한다.
4. 노션·Gemini에서 온 텍스트는 `innerHTML`로 넣지 않는다(`textContent`). 같은 github.io의 모든 저장소에 지킨다.
5. 노션 키 권한은 사용자가 최소로 준다(integration을 템플릿 페이지에만 연결하도록 안내).

## 2. DB 쪽 (04 문서 `integrations`에 반영할 규칙)

- 일반 테이블에는 **Vault 비밀의 id, 끝 4자리(hint), `updated_at`** 만 둔다. 키 원문은 `vault.secrets`에만.
- **저장은 RPC 하나로만** (브라우저에서 호출):
  - `security definer set search_path = ''`, 함수 안에서 `auth.uid()`로 사용자를 정한다 → 남의 `user_id`로 저장 불가.
  - 형식 검사(노션: `^(ntn_|secret_)`, 페이지·DB id: `^[0-9a-f]{32}$`) 후 처음이면 `vault.create_secret`, 있으면 `vault.update_secret` + `updated_at = now()`.
  - 테이블에는 insert/update 정책을 두지 않고 select·delete(본인 행)만 둔다.
- **조회(복호화)는 service_role 전용 RPC**: `vault.decrypted_secrets` 조인. Edge Function만 부른다.
- **권한 회수 주의:** Supabase는 `public` 스키마 새 함수의 실행 권한을 `anon`, `authenticated`에 **직접** 준다. `revoke ... from public`만으로는 안 되고 역할 이름을 적는다.
  ```sql
  revoke execute on function public.save_notion_key(...) from public, anon;
  grant  execute on function public.save_notion_key(...) to authenticated;
  revoke execute on function public.get_notion_key(uuid) from public, anon, authenticated;
  grant  execute on function public.get_notion_key(uuid) to service_role;
  ```
- **삭제 시 Vault 정리 트리거:** 연결 행이 지워지면(계정 삭제 cascade 포함) `after delete` 트리거가 `delete from vault.secrets where id = old.secret_id`.
- 배포 전 점검 쿼리(모두 `false`여야 함, P0-2 pgTAP에 넣는다):
  ```sql
  select has_function_privilege('anon',          'public.get_notion_key(uuid)', 'execute'),
         has_function_privilege('authenticated', 'public.get_notion_key(uuid)', 'execute');
  ```

## 3. 중계 서버 쪽

원문의 GAS 흐름: ① 토큰 확인(5분 캐시) → ② 앱별 **허용 경로 목록** 검사 → ③ 키 조회(10분 캐시, 캐시 키 = `uid + version(updated_at)` 해시) → ④ 노션 호출. 노션이 401이면 그 캐시를 지운다.

ULevelP(Edge Function)에 옮길 때:

| 원문(GAS) | ULevelP(Edge Function) |
| --- | --- |
| 토큰을 body로 받음 | `Authorization` 헤더. 클라이언트는 `supabase.functions.invoke`로 부름(토큰 자동). 사용자 확인은 `auth.getClaims(token)` 또는 `auth.getUser(token)` |
| 키 캐시(ScriptCache) + `updated_at` 버전 | **캐시 없음.** 같은 데이터센터에서 service_role로 `get_*_key`를 부르면 됨. 키 재등록은 바로 반영 |
| 허용 경로 목록 `ROUTES_BY_APP` | 범용 노션 프록시를 열지 않는다. 함수마다 하는 일이 정해져 있다(`notion-push`, `notion-pull`, `integration-check`, `analyze-video`). 클라이언트가 노션 경로를 고르는 API는 만들지 않는다 |
| 항상 200 + body에 오류 | 실제 HTTP 상태 + body `{ ok: false, source: 'proxy' \| 'notion' \| 'gemini', status, code, message, retryAfter }`. 예외가 나도 CORS 헤더를 붙인다 |
| CORS 불가 → `text/plain` | `OPTIONS` 응답, `ALLOWED_ORIGINS = https://hunseokc.github.io,http://localhost:3000` (`supabase secrets set`). 비어 있으면 헤더가 `undefined`가 되니 배포 전 확인 |
| `keepAlive` 트리거(7일 일시정지 방지) | pg_cron(`notion-push` 1분)이 활동으로 잡히는지 P4-2에서 확인. 안 되면 하루 1회 외부 호출을 따로 둔다 |
| 429 → `retryAfter`초 기다려 재시도 | 같음. push는 다음 실행에 다시(03 6.4) |
| `Notion-Version` 고정 | `2022-06-28` 유지. `2025-09-03`부터 DB가 data source로 바뀌어 조회 경로가 달라지므로, 올릴 때 push·pull·check를 같이 고친다 |

## 4. 클라이언트 쪽 (D14 키 등록 캐시)

- 원문 화면 상태: 로그아웃 / 로그인했지만 연결 없음 → 키 등록 화면 / 연결됨 → 설정에 "끝 4자리 · 마지막 갱신일 · 연결 해제".
- `getConnection()` 오류(네트워크, 프로젝트 일시정지)는 **"키 없음"으로 처리하지 않고** 오류로 던진다. (흔한 실수: 키를 등록했는데 계속 등록 화면이 뜸)
- 키 입력란은 `type="password"`, `autocomplete="off"`. 저장 뒤에는 끝 4자리만 보인다.
- 저장 직후 "연결 확인"을 부르고 결과로 분기: 노션 404 `object_not_found` → "템플릿 페이지에 연결(Connections)을 추가하세요"(가장 많이 빠뜨리는 단계), 노션 401 → 키 재입력.
- ULevelP 캐시: localStorage에 `{ notion: { hint, updatedAt } | null, gemini: { hint, updatedAt } | null, checkedAt }`만 둔다(키 원문 없음). 키 저장·해제 때 갱신, 서버가 `NO_KEY`·키 오류(401/403)를 주면 지우고 다시 읽는다. 버튼 활성화는 이 캐시로 하고, 최종 거부는 서버가 한다.

## 5. 오류 코드 → 화면 처리 (원문 표 기준)

| source | status / code | 화면 처리 |
| --- | --- | --- |
| proxy | 401 `UNAUTHORIZED` | 로그인으로 |
| proxy | 412 `NO_KEY` | 캐시 지우고 SETTING 키 칸으로 |
| proxy | 500 `DB_ERROR` / `INTERNAL` | "잠시 후 다시 시도해 주세요" |
| notion | 401 `unauthorized` | "노션 키를 다시 등록해 주세요" |
| notion | 404 `object_not_found` | 페이지 연결 방법 안내 |
| notion | 429 `rate_limited` | 자동 재시도(`retryAfter`), 그래도 실패하면 안내 |
| gemini | 400/403 키 오류 | 캐시 지우고 "Gemini 키를 확인해 주세요" |
| network | `NETWORK` | "연결할 수 없어요" + 다시 시도 |

## 6. 온보딩 문구 (P4-1 SETTING 안내에 쓸 것)

1. https://www.notion.so/profile/integrations → 새 연결 → 내부(Internal), 권한은 콘텐츠 읽기·업데이트·삽입만(사용자 정보 끔), 시크릿(`ntn_…`) 복사. 워크스페이스 소유자만 만들 수 있다.
2. **템플릿을 복제한 페이지 ••• → 연결 → 방금 만든 연결 추가** (하위 DB는 자동 포함)
3. ULevelP SETTING에 키와 DB 링크를 붙여넣고 "연결 확인"
4. 끊기: SETTING → 연결 해제(저장된 키 삭제). 노션에서 시크릿을 재발급해도 바로 무효.

주소는 배포 전에 노션 공식 문서와 다시 맞춰 본다(integration → connection 이름 변경 중).
