# 주니어 체크리스트 (리뷰 지적 누적)

PR을 올리기 전에 모든 항목으로 diff를 점검한다. 작은 판단이 필요할 때도 이 파일을 기준으로 삼는다. 운영 방법은 [협업_시니어주니어.md](협업_시니어주니어.md) 6·7절에 있다.

- **형식:** `- [ ] 규칙 — 출처(PR #n 리뷰 k번) — 확인 방법`
- 지적을 그대로 옮기지 않고, 다음 step에도 쓸 수 있게 **일반화**해서 적는다.
- 같은 종류의 지적이 다시 나오면 새 항목을 만들지 않고, 그 항목 앞에 **`중요`** 를 붙이고 출처를 덧붙인다.

## API·호환
- [ ] 기존 API(`/api/chord` 등 계산 API)의 응답·에러 모양을 바꾸지 않는다. 새 형식(`{ ok, source, status, code, message }`)은 `/api/v1`에만 쓴다 — PR #8 리뷰 1번 — 기존 API 테스트가 원래 모양(`{error}`, 404의 `apis`)을 검사하는지 확인
- [ ] 없는 경로의 404 처리는 인증보다 앞에 둔다(토큰 없이도 404) — PR #8 리뷰 9번 — 토큰 없이 없는 경로를 curl로 호출해 401이 아니라 404가 나는지 확인
- [ ] 다른 앱(`guitar-practice`) 데이터로 대신 채워 보여 주지 않는다. 조회는 `app_id = 'ulevelp'`로 한정한다 — PR #8 리뷰 10번 — 쿼리에 `app_id` 조건이 있는지 확인
- [ ] 동일 의미의 응답 본문(예: `{ "ok": true }`)은 라우트 간 작성 방식(`buildJsonObject` 등)을 통일하고 미사용 import를 남기지 않는다 — PR #12 리뷰 5번, 6번 — diff에서 불필요한 import 및 응답 빌더 일관성 확인
- [ ] multipart의 텍스트 파트(JSON 등)는 `FormItem`과 `FileItem`을 모두 받는다(브라우저 `Blob`은 `filename`이 붙는다) — K1-3 M4 / PR #15 — `filename`이 붙은 텍스트 파트 테스트가 있는지 확인
- [ ] multipart의 텍스트 파트(metadata 등)를 읽을 때 말없이 잘라 읽거나 무제한으로 받지 않고, 상수 한도(`한도 + 1`)를 검사하여 초과 시 즉시 400(`INVALID_INPUT`)을 반환한다 — PR #15 리뷰 3번 — 한도 초과(65KB 등) 시 400 반환 단위 테스트 확인

## 인증·데이터 수명
- [ ] 삭제한 사용자가 남은 토큰으로 다시 생성되지 않게 막는다(삭제 기록 확인 또는 Auth 사용자 삭제) — PR #8 리뷰 2번 — 삭제 후 같은 토큰으로 호출하는 테스트
- [ ] **중요** 로그아웃·계정 전환·`/me` 실패 시 이전 사용자 상태(`currentMe`, `ulp:keys`, 진행 중인 곡 `st.song`, 녹음 대기 객체 `rec.take.song`, 녹음 진행 중 메타데이터 `rec.meta.song` 등)를 모두 초기화하고, 비동기 응답 도착 시 요청 당시 uid를 확인하여 이전 사용자의 지연 응답이 새 사용자 화면을 덮어쓰지 않게 버린다 — PR #9 리뷰 4번, PR #13 리뷰 4번, PR #13 2차 리뷰 1번, PR #18 리뷰 1번 — uid가 바뀌는 분기에서 이전 사용자 소유 데이터/식별자 잔존 여부 및 비동기 응답 도착 시 요청 당시 uid 일치 검증 확인
- [ ] 로그아웃은 이 브라우저만 한다(`signOut({ scope: 'local' })`) — PR #9 리뷰 5번 — `signOut` 호출 인자 확인

## 에러 처리
- [ ] 비동기 호출(`await`)은 실패 경로를 처리하고, 사용자에게 보이는 반응(메시지, 이동)을 남긴다. 빈 `catch`나 삼킨 rejection은 쓰지 않는다 — PR #9 리뷰 6번, 2번 — `catch`마다 처리 내용이 있는지 확인
- [ ] Promise를 반환하는 비동기 인터페이스(API 래퍼 등)는 실패 시 동기로 throw하지 않고 항상 Promise reject를 반환한다(호출부의 `.catch()` 체인이 끊기거나 unhandled 예외가 되지 않도록 한다) — PR #13 리뷰 1번 — 비동기 인터페이스를 동기 try-catch 없이 `() => fn()`으로 `assert.rejects` 테스트하여 동기 예외 발생 여부 확인
- [ ] 상위 리소스(곡 등)에 종속된 하위 리소스(녹음 take 등) 등록/업로드 시 404(상위 리소스 삭제) 응답을 받으면 캐시된 상위 리소스 참조를 null로 초기화하여 재시도 시 새 리소스를 생성하거나 유효한 ID로 복구할 수 있게 한다 — PR #13 2차 리뷰 2번 — 404 발생 시 상위 객체 참조 null 처리 및 사용자 복구 안내 문구 확인
- [ ] 외부 조회(JWKS, HTTP)가 실패해도 매 요청 재시도하지 않는다. 실패 시각을 기록하고 재시도 간격을 둔다 — PR #8 리뷰 3번 — 실패 테스트에서 두 번째 요청이 외부 호출을 하지 않는지 확인
- [ ] 목록 중 항목 하나가 깨져도 전체를 버리지 않는다(항목별 `runCatching`) — PR #8 리뷰 5번 — 불량 항목 1개를 넣은 테스트
- [ ] 외부 저장소/원격 자원에 먼저 쓰고 DB에 기록하는 2단계 보상 흐름에서는 코루틴이 취소(`CancellationException`)되어도 정리 작업이 돌 수 있도록 `withContext(NonCancellable)`로 감싼다. 단, `CancellationException`이 반드시 롤백을 의미하지는 않으므로(커밋 직후 취소 복귀 가능), 외부 자원을 정리하기 전에 DB에 이미 커밋된 기록이 있는지 확인하고 있으면 삭제를 건너뛴다 — PR #12 리뷰 1번, 2차 리뷰 1번·3번 — 취소 시 외부 자원 고아 방지 및 커밋된 파일 오삭제 방지 확인

## 성능·동시성
- [ ] suspend 흐름 안의 blocking 호출(HTTP, 파일)은 `withContext(Dispatchers.IO)`로 감싼다 — PR #8 리뷰 4번 — `send`/`execute`/파일 I/O 호출 위치 확인
- [ ] Exposed `dbQuery` 사용 시 `newSuspendedTransaction(Dispatchers.IO)`처럼 디스패처를 컨텍스트 인자로 단독 전달하면 부모 Job 계층이 끊겨 취소가 트랜잭션으로 전파되지 않으므로, `withContext(Dispatchers.IO) { newSuspendedTransaction(db = db) { ... } }`와 `ensureActive()`로 부모 컨텍스트 계층과 취소 시 롤백을 보장한다 — PR #12 CI 수정 — 코루틴 취소 시 DB 트랜잭션이 롤백되는지 확인
- [ ] 요청마다 반복되는 쓰기(INSERT/UPDATE)를 만들지 않는다. 존재를 먼저 확인하거나 한 번만 실행한다 — PR #8 리뷰 8번 — 같은 요청을 두 번 보내고 쓰기 쿼리 횟수 확인
- [ ] 같은 API를 이벤트마다 중복 호출하지 않는다(필요한 이벤트·값이 바뀔 때만) — PR #9 리뷰 8번 — 페이지 로드 1회에 네트워크 호출 횟수 확인
- [ ] 상태 변경 알림(Auth `onChange` 등)이나 반복 이벤트 리스너 안에서 실패 가능한 사용자 확인(`confirm`/`prompt` 등)이나 무거운 비동기 작업을 매번 재실행하지 않는다. 세션/페이지 수명 단위의 플래그(uid별 시도 여부 등)를 두어 실패 시 다음 페이지 로드 전까지 반복 창을 억제한다 — PR #13 리뷰 3번 — 실패 후 토큰 갱신 등의 이벤트가 발생할 때 확인 창이 다시 뜨지 않는지 확인
- [ ] 비동기 초기화(start 함수 등) 도중 도착하여 가드 조건(`!started` 등)으로 건너뛴 상태 변경/인증 이벤트는 초기화 완료 직후 명시적으로 현재 상태(`me`, `uid` 등)를 점검하여 1회성 작업(마이그레이션 등)이 누락되지 않도록 보장한다 — PR #13 2차 리뷰 8번 — 초기화 비동기 대기 중 이벤트가 먼저 발생해도 초기화 직후 작업이 실행되는지 확인
- [ ] 부분 갱신으로 충분하면 전체 재렌더로 입력 중 상태를 날리지 않는다(녹음 삭제 등 항목 변경 시 해당 요소만 갱신/삭제하여 다른 카드의 미저장 textarea나 미디어 재생 상태를 보존) — PR #18 리뷰 2번 — 부분 변경 시 전체 재렌더링으로 다른 폼 입력값이나 오디오 재생이 초기화되지 않는지 확인

## 테스트
- [ ] **중요** 단언을 항상 참인 조건으로 바꾸지 않는다(`A || B`에서 B가 이미 보장되는 경우, 테스트 헬퍼가 타입을 왜곡해 실제 검증하려던 단계를 가리는 경우, Promise reject를 검증하는 `assert.rejects`에 `async () =>`를 씌워 비동기 함수가 동기로 throw하는 버그를 놓치는 경우 등). 테스트를 고치면 이유를 결과 파일에 적는다 — PR #8 리뷰 6번, PR #11 리뷰 1번, PR #13 리뷰 1번 — 단언이 실패할 수 있는 입력이 있는지 및 동기 throw가 비동기 reject로 왜곡되지 않는지 따져 본다
- [ ] 정리/실패 결과 검증 시 행 수뿐 아니라 대상 식별자·키가 실제 남은 정상 데이터와 배타적으로 일치하는지 단언한다 — PR #12 리뷰 2번 — 단언에 식별자/키 일치 및 배타성 검사 포함 여부 확인
- [ ] 테스트 DB는 Docker 임시 컨테이너만 쓴다. 외부·공유 DB를 테스트에 연결하지 않는다 — K0-2 리뷰 — 테스트 설정에 원격 DB URL이 없는지 확인

- [ ] **중요** 완료 기준을 실제로 실행하지 않았으면 "완료"로 표시하지 않는다. 사람이 할 일(실환경 점검 등)이 남았으면 단계 표와 결과 파일 모두 상태를 `진행`으로 두고 남은 일을 적으며, 묶음 완료 안내나 다음 묶음 시작 멘트를 미리 적지 않는다 — PR #9 리뷰 7번, PR #13 리뷰 2번 — 결과 파일에 실행 출력이 붙어 있는지 및 진행 파일 단계 표와 결과 파일의 상태가 일치하는지 확인
- [ ] 작업과 무관한 파일(개인 백업, 메모)과 쓰지 않는 코드(DTO 등)를 커밋하지 않는다 — PR #8 리뷰 7번 — `git status`·`git diff --stat`으로 명세 파일 목록과 비교
- [ ] 의존성은 보안 패치가 반영된 고정 버전을 쓴다 — K0-2 리뷰(pgjdbc 42.7.7) — `build.gradle.kts` 버전 확인
- [ ] iframe(노션 임베드) 같은 다른 실행 환경에서도 주요 흐름(로그인 등)이 이어지는지 확인한다 — PR #9 리뷰 10번 — 임베드 분기 코드에서 다음 동작이 끊기지 않는지 확인
