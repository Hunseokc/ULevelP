# 주니어 체크리스트 (리뷰 지적 누적)

PR을 올리기 전에 모든 항목으로 diff를 점검한다. 작은 판단이 필요할 때도 이 파일을 기준으로 삼는다. 운영 방법은 [협업_시니어주니어.md](협업_시니어주니어.md) 6·7절에 있다.

- **형식:** `- [ ] 규칙 — 출처(PR #n 리뷰 k번) — 확인 방법`
- 지적을 그대로 옮기지 않고, 다음 step에도 쓸 수 있게 **일반화**해서 적는다.
- 같은 종류의 지적이 다시 나오면 새 항목을 만들지 않고, 그 항목 앞에 **`중요`** 를 붙이고 출처를 덧붙인다.

## API·호환
- [ ] 기존 API(`/api/chord` 등 계산 API)의 응답·에러 모양을 바꾸지 않는다. 새 형식(`{ ok, source, status, code, message }`)은 `/api/v1`에만 쓴다 — PR #8 리뷰 1번 — 기존 API 테스트가 원래 모양(`{error}`, 404의 `apis`)을 검사하는지 확인
- [ ] 없는 경로의 404 처리는 인증보다 앞에 둔다(토큰 없이도 404) — PR #8 리뷰 9번 — 토큰 없이 없는 경로를 curl로 호출해 401이 아니라 404가 나는지 확인

- [ ] 날짜/시각 필드를 직렬화할 때는 일관되게 `DateTimeFormatter.ISO_INSTANT.format(t.toInstant())`(`...Z`)를 사용하여 호스트/DB 드라이버의 로컬 오프셋(`+09:00` 등)이 노출되지 않도록 고정한다 — PR #27 리뷰 3번 — API 응답의 시간 필드가 UTC `Z`로 끝나는지 확인

## 에러 처리
- [ ] **중요** 비동기 호출(`await`)은 실패 경로를 처리하고, 사용자에게 보이는 반응(메시지, 이동)을 남긴다. 빈 `catch`나 삼킨 rejection은 쓰지 않는다 — PR #9 리뷰 6번·2번, PR #23 리뷰 3번, PR #25 리뷰 4번 — `catch`마다 사용자 반응(메시지 표시 등) 처리 내용이 있는지 확인
- [ ] Promise를 반환하는 비동기 인터페이스(API 래퍼 등)는 실패 시 동기로 throw하지 않고 항상 Promise reject를 반환한다(호출부의 `.catch()` 체인이 끊기거나 unhandled 예외가 되지 않도록 한다) — PR #13 리뷰 1번 — 비동기 인터페이스를 동기 try-catch 없이 `() => fn()`으로 `assert.rejects` 테스트하여 동기 예외 발생 여부 확인
- [ ] 상위 리소스(곡 등)에 종속된 하위 리소스(녹음 take 등) 등록/업로드 시 404(상위 리소스 삭제) 응답을 받으면 캐시된 상위 리소스 참조를 null로 초기화하여 재시도 시 새 리소스를 생성하거나 유효한 ID로 복구할 수 있게 한다 — PR #13 2차 리뷰 2번 — 404 발생 시 상위 객체 참조 null 처리 및 사용자 복구 안내 문구 확인
- [ ] 외부 조회(JWKS, HTTP)가 실패해도 매 요청 재시도하지 않는다. 실패 시각을 기록하고 재시도 간격을 둔다 — PR #8 리뷰 3번 — 실패 테스트에서 두 번째 요청이 외부 호출을 하지 않는지 확인
- [ ] **중요** 목록 중 항목 하나가 깨져도 전체를 버리지 않는다(항목별 `runCatching` 또는 세부 try-catch로 격리) — PR #8 리뷰 5번, PR #25 리뷰 2번 — 불량 항목 1개를 넣은 테스트
- [ ] **중요** 외부 저장소/원격 자원에 먼저 쓰고 DB에 기록하는 2단계 보상 흐름에서는 코루틴이 취소(`CancellationException`)되어도 정리 작업이 돌 수 있도록 `withContext(NonCancellable)`로 감싼다. 단, `CancellationException`이 반드시 롤백을 의미하지는 않으므로(커밋 직후 취소 복귀 가능), 외부 자원을 정리하기 전에 DB에 이미 커밋된 기록이 있는지 확인하고 있으면 삭제를 건너뛴다 — PR #12 리뷰 1번, 2차 리뷰 1번·3번, PR #22 리뷰 2번 — 취소 시 외부 자원 고아 방지 및 커밋된 파일 오삭제 방지 확인
- [ ] 원격/외부 서비스 호출 실패(5xx, 타임아웃 등)를 임의로 삼킨 뒤 로컬 매핑·연결 상태(링크 DB 등)를 지우지 않는다. 이미 존재하지 않음(404) 등 멱등한 성공 조건 외의 오류는 재시도할 수 있도록 예외를 전파하여 작업 횟수(attempts)를 늘리고 로컬 상태를 보존한다 — PR #24 리뷰 1번 — 외부 오류 발생 시 로컬 링크 보존 및 attempts 증가 단위 테스트 확인
- [ ] 외부에 자원을 생성·업로드하는 작업(파일 업로드, 블록 추가 등)은 재시도나 중복 대기열 처리가 발생해도 한 번만 반영되도록 시작 전 기존 연동 링크·식별자의 존재를 먼저 확인하여 멱등성을 보장하고, 긴 외부 작업 직전에는 점유(lease)를 연장한다 — PR #24 리뷰 2번 — 동일 항목의 중복 outbox 또는 재시도 시 외부 API 생성/업로드 호출이 1회로 제한되는지 확인
- [ ] suspend 함수 내에서 `runCatching`이나 무분별한 `catch (e: Exception)`으로 코루틴 취소 예외(`CancellationException`)를 삼키지 않는다. 부가적인 보조 작업(속성 첨부 등)의 실패를 격리할 때도 `CancellationException`은 반드시 다시 던져(`throw e`) 취소 신호가 상위 코루틴으로 전파되도록 한다 — PR #24 리뷰 3번 — catch 블록에 `catch (e: CancellationException) { throw e }`가 포함되어 있는지 확인
- [ ] 크론 등 배치 작업에서 성격이 다른 여러 독립적인 단계(동기화, 쓰레기통 정리, 타임아웃 정리 등)를 연속 실행할 때는 선행 단계의 일시적 실패가 후행 단계의 필수 정리 작업을 중단시키지 않도록 단계별로 예외를 격리한다 — PR #24 리뷰 4번 — 특정 정리 단계에서 예외가 발생해도 다음 정리 작업이 실행되는지 확인
- [ ] 외부 입력/문자열에서 숫자를 파싱할 때는 비정상적으로 큰 값이나 오버플로로 인한 런타임 오류(`NumberFormatException` 등)를 방지하기 위해 `toIntOrNull()`을 사용하여 안전하게 null/fallback 처리한다 — PR #27 리뷰 5번 — 아주 큰 숫자 문자열 입력 시 예외 발생 없이 null 처리되는지 확인

## 성능·동시성
- [ ] 잠금(FOR UPDATE)으로 보호하는 검사·삭제 로직은 반드시 잠금 획득 뒤에 조회하고, 삭제는 조건식이 아닌 조회한 id 목록(inList)으로 제한하여 동시 요청 시 고아 리소스 발생 및 outbox 누락을 방지한다 — PR #33 리뷰 1·2번 — 잠금 획득 순서 및 deleteWhere의 inList 조건 확인
- [ ] suspend 흐름 안의 blocking 호출(HTTP, 파일)은 `withContext(Dispatchers.IO)`로 감싼다 — PR #8 리뷰 4번 — `send`/`execute`/파일 I/O 호출 위치 확인
- [ ] `java.net.http.HttpClient`를 코루틴 suspend 함수에서 사용할 때는 블로킹 `send()` 대신 `sendAsync(...).await()`(`kotlinx.coroutines.future.await`)를 사용하여 상위 코루틴 타임아웃(`withTimeout`)이나 취소 신호가 소켓 I/O에 즉시 전파되도록 한다 — PR #27 리뷰 6번 — HTTP 호출 도중 코루틴 취소 시 즉각 중단되는지 확인
- [ ] Exposed `dbQuery` 사용 시 `newSuspendedTransaction(Dispatchers.IO)`처럼 디스패처를 컨텍스트 인자로 단독 전달하면 부모 Job 계층이 끊겨 취소가 트랜잭션으로 전파되지 않으므로, `withContext(Dispatchers.IO) { newSuspendedTransaction(db = db) { ... } }`와 `ensureActive()`로 부모 컨텍스트 계층과 취소 시 롤백을 보장한다 — PR #12 CI 수정 — 코루틴 취소 시 DB 트랜잭션이 롤백되는지 확인

## UI·상태 관리
- [ ] 미디어 요소의 `src`는 `''`를 넣어 지우지 않는다(getter가 문서 URL을 돌려준다). `removeAttribute('src')`와 `load()`로 지우고, 무엇을 실었는지는 `dataset`으로 따로 기록한다 — PR #19 리뷰 1번 — 오디오 src 초기화 후 play 호출 시 문서 URL 요청 여부 및 dataset 식별자 확인
- [ ] 선택·필터가 바뀌어도 개수가 같으면 초기화 분기를 타지 않는 경우가 있다. 개수가 아니라 **식별자 비교**로 바뀌었는지 판단한다 — PR #19 리뷰 2번 — 3번째 항목 선택 등 요소 교체 시 슬롯/오디오가 새 식별자로 재설정되는지 확인
- [ ] **중요** 상위 상태(악기 종류, 현 수, 카테고리 등)에 종속된 하위 옵션·파라미터(줄 쌍 `pair`, 인덱스 `sel`, 하위 모드 등)는 상위 상태 변경 시 하위 상태의 정규화를 비동기 `useEffect`에만 의존하지 않는다. `useEffect`는 렌더링 커밋 이후에 실행되므로 렌더링 도중 이전 하위 상태 값으로 엔진/계산 함수가 동기 호출되어 범위 초과(`IndexOutOfBounds` / `invalid pair`)로 크래시된다. 반드시 (1) 렌더 타임에 유효 범위를 보장하는 `effective*` 정규화 값을 동기 계산해 렌더/엔진에 전달하고, (2) 상위 상태를 변경하는 이벤트 핸들러에서도 하위 상태를 원자적(동기적)으로 함께 갱신한다 — PR #41 리뷰 1번 — 상위 상태 변경(예: 6현 기타 [4, 5] -> 4현 베이스) 시 첫 렌더에서 하위 엔진 호출 에러가 없는지 및 단위/정적 테스트 확인
- [ ] **중요** 미디어(오디오/비디오) 재생 주소의 비동기 발급/조회(`getUrl`, `fetchMediaObjectUrl` 등)는 사용자 상호작용(슬롯 선택 변경, A/B 페어 교체, 삭제)이나 인증 변경(로그아웃, 계정 전환)보다 오래 살아남아 뒤늦게 resolve되어 이전 URL을 할당하고 재생(`play()`)을 시작하는 레이스 컨디션을 유발할 수 있다. 비동기 재생 요청 진입 시 요청 토큰(`reqToken`)과 현재 계정(`uid`)을 캡처하고, 매 `await` 복귀 후 및 `src` 할당과 `play()` 호출 직전에 (1) 요청 토큰 일치 여부, (2) 현재 인증/계정 일치 여부, (3) 슬롯/요소가 여전히 동일한 식별자(`take.id`)를 가리키고 있는지를 검증하며, 페어/선택 교체나 계정 전환·로그아웃 시 요청 토큰을 즉시 증가/무효화한다 — PR #43 리뷰 1번 — A/B 슬롯 비동기 로드 중 페어 교체/로그아웃 시 이전 오디오 할당 및 재생 방어 확인
- [ ] **중요** 화면을 새로 만들거나 배치를 바꾸면 `개발산출물/프론트_정렬규격.md` §1 순서대로 한다: 배치 약속(`data-align-group`) 먼저 → 그 화면 `test/e2e/layout/<화면>.spec.js`(`layoutSuite`)를 추가·갱신해 수정 전 코드에서 실패 확인 → 구현 → 실패 0 → `LAYOUT_SHOTS=1` 4개 폭 스크린샷을 §6 질문(Q1~Q9)으로 검토해 결과 파일에 표로. 가로 스크롤 검사(`layout.spec.js`)만으로는 정렬이 깨진 것을 못 잡는다. 공통 검사 G0~G8: 카드 밖 넘침, 형제 겹침, 의도치 않은 말줄임, 가로 스크롤, 금지 색, 제목 아래 처짐, 터치 크기, 간격. 상태는 `support/mock-app.js` `STATES`(빈·데이터 있음·로그인) × 390·768·1150·1280px. 예외는 `data-layout-ignore="G3: 사유"`(의도), 아직 안 고친 실패는 `known`(고칠 step 적기) — 규칙을 끄지 않는다. 흔한 원인: 카드에 `justify-content: space-between`, 그리드 칸보다 넓은 고정폭 자식, 칸을 늘리는 `flex: 1`, 한 줄 `nowrap` 말줄임, 옛 CSS 이식 누락·`:global(.모듈클래스 …)` 선택자 실수(검사기가 못 잡고 스크린샷으로만 잡힘), 390(안쪽 폭 약 270px)에서 두 줄이 되는 긴 필 문구(손으로 재지 말고 `settings.spec.js` `collectWrappedPills` 같은 필 한 줄 검사를 둔다) — 홈 정렬 수정(진행_홈정렬.md), FT-3(완료/진행_프론트정렬규격.md) — `test/e2e/layout/home.spec.js`를 본보기로 해당 화면 spec이 있고 수정 전 코드에서 실패했는지, 결과 파일에 스크린샷 검토 표가 있는지 확인
