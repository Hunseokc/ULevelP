## 3. B0가 쓸 값

### 3.1 `window.ULData` API 표

```js
// 1. 로그인 여부 확인 (동기)
window.ULData.isLoggedIn() // boolean

// 2. 곡 목록 조회 (상태 필터 생략 가능)
await window.ULData.songs.list(status) // SongDto[]

// 3. 비디오 ID로 곡 조회
await window.ULData.songs.byVideo(videoId) // SongDto | null

// 4. 곡 신규 등록
await window.ULData.songs.create({ videoId, title, artist, rate }) // SongDto

// 5. 플레이어 진행 저장 (8개 키만 필터링하여 전송, keepalive 경로 지원)
await window.ULData.saveProgress({
  songId, pos, a, b, rate, date, addSeconds, addLoops
}, { keepalive: false }) // { ok, keep, sessionId, totalSeconds, minutes, pendingSeconds }

// 6. 녹음 멀티파트 업로드 (8개 키 metadata Blob + audio 파일 Part)
await window.ULData.takes.upload({
  songId, date, recordedAt, a, b, rate, durationSec, mime
}, blob) // TakeDto

// 7. 로컬 기기 기록 계정 이관 (confirm 창을 통한 사용자 승낙 후 100건 배치 전송)
await window.ULData.runLocalMigration() // { status: 'skipped' | 'done' | 'failed', created, skipped, message }
```

## 4. 명세와 달라진 점 및 겪은 문제

- **명세와 달라진 점:** 없음. 모든 파일 목록, 시그니처, 8개 키 정제 규칙, 에러 문구, 이벤트 리스너 동작이 명세 1:1로 구현되었습니다.
- **겪은 문제 (Node 22+ vm 객체 assert.deepEqual strict 프로토타입 불일치):**
  - Node 22+ 내장 `node:assert/strict`의 `assert.deepEqual`은 서로 다른 `vm` 컨텍스트의 `Object.prototype`을 가진 객체 비교 시 내용이 같아도 `Values have same structure but are not reference-equal` 오류를 발생시킴.
  - `test/data.test.js`에서 반환 객체를 `{ ...res }` 형태로 얕은 복사하여 비교하도록 수정하여 해결함.
- **PR #13 시니어 리뷰 코멘트 반영 (1~4번):**
  1. `saveProgress` 비로그인 시 동기 예외 throw 버그 수정: `try { requireLogin(); } catch (e) { return Promise.reject(e); }`로 감싸 Promise reject를 보장함. `test/data.test.js` D1의 `assert.rejects` 호출을 `() => ULData.xxx(...)`로 수정하여 비동기 인터페이스의 동기 throw 여부를 엄격히 검증하도록 개선함 (리뷰 1번).
  2. 진행 파일 `진행_코틀린서버.md` 단계 표의 K1-3 상태를 `진행 (M2~M5 사람 확인 대기)`으로 동기화하고 조기 작성된 A 묶음 완료 및 B0 멘트를 대기 상태로 수정함 (리뷰 2번).
  3. `practice.js`에 uid별 `migrationAttempted` 플래그를 추가하여 이관 실패 시 동일 페이지 내 `onChange` 알림마다 확인 창이 반복해서 뜨지 않도록 억제함 (리뷰 3번).
  4. `practice.js`의 `onChange` uid 변경 분기에서 녹음 대기 객체의 곡 정보(`if (rec.take && !rec.take.done) rec.take.song = null;`)를 초기화하여 이전 사용자의 `songId`로 업로드 요청(404 발생)되는 문제를 방지함 (리뷰 4번).
  5. 5번(설계 변경)은 시니어 몫이므로 손대지 않음 (B0 명세에서 처리 예정).
- **M4 실환경 녹음 업로드 멀티파트 수신 문제 해결:**
  - **증상:** 브라우저에서 녹음 업로드 시 400 Bad Request (`metadata 파트가 필요합니다.`) 에러 발생.
  - **원인:** 브라우저 표준에 따라 `FormData`에 `Blob`을 추가하면 `filename="blob"` 헤더가 붙어 Ktor 서버의 `receiveMultipart()`가 이를 `PartData.FormItem`이 아닌 `PartData.FileItem`으로 분류함. 기존 `TakeRoutes.kt`는 `metadata`를 오직 `FormItem`에서만 읽도록 되어 있어 파트가 누락됨.
  - **해결:** `TakeRoutes.kt`의 `PartData.FileItem` 분기에서도 `part.name == "metadata"`일 때 스트림을 읽어 UTF-8 문자열로 변환하도록 보완하고, `TakeApiTest.kt`에 `T20 브라우저 FormData Blob 형태의 metadata 수신 (FileItem 파싱)` 단위 테스트를 추가함. Supabase 대시보드 Storage에 `takes` 버킷 생성 후 업로드 및 재생 정상 동작 최종 확인 완료.
