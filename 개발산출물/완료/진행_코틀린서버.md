## 1. 목표와 근거

- **목표:** 노션·Apps Script·GitHub Actions에 기대던 ULeveLP를 **구글 로그인만으로 쓰는 다중 사용자 웹 서비스**로 전환하되, 백엔드 비즈니스 로직·노션 동기화·Gemini 영상 분석·지판/건반 SVG 생성을 **Kotlin (Ktor) + Google Cloud Run 단일 컨테이너 서버**로 통합한다.
- **저장소 분리 원칙:**
  - `Hunseokc/guitar-practice` = 노션 기반 원본(`upstream` 원격 참고 전용, push 금지).
  - `Hunseokc/ULevelP` = 다중 사용자 웹 서비스 저장소(`origin`).
- **근거 문서 (구현 기준 — 바꾸면 문서도 같이 고친다):**
  - [docs/01-project-plan.md](../docs/01-project-plan.md): 목표 G1~G6, 아키텍처, 기술 스택, 결정 KC-D1~D10, 로드맵
  - [docs/02-requirements.md](../docs/02-requirements.md): 기능 요구사항(`FR-*`)·비기능 요구사항(`NFR-*`) 인수 조건
  - [docs/03-api-spec.md](../docs/03-api-spec.md): 도메인별 REST API 엔드포인트 요청·응답 JSON 명세 및 오류 코드
  - [docs/04-db-design.md](../docs/04-db-design.md): PostgreSQL 표준 DDL(`V1__init.sql`), AES-256-GCM 키 암호화, 동시성 SQL 패턴, 노션 템플릿 1:1 매핑표
- **작업 규칙:** 저장소 루트 [CLAUDE.md](../CLAUDE.md)를 따른다(메뉴얼 vs 자유, 검증, Git, 세션 분리).

## 2. 핵심 결정 사항

| ID | 내용 | 상태 |
| --- | --- | --- |
| **KC-D1** | 백엔드는 **Kotlin 2.0 + Ktor 3.x + JDK 21 (Alpine)** 단일 컨테이너로 만들어 **Google Cloud Run**에 배포한다. 기존 `Code.gs`(Apps Script), `analyze.py`(GitHub Actions)를 모두 이 서버로 통합한다 | 확정 |
| **KC-D2** | 코드 연습실(`chords.html`)의 프런트엔드 계산 엔진(`public/lib/voicing.js`, `theory.js`)은 브라우저 무지연 동작을 위해 그대로 유지한다. 로컬/외부용 `/api/*` 계산 API는 Ktor 서버에서도 동일 스펙으로 제공한다 | 확정 |
| **KC-D3** | DB는 PostgreSQL 16+(Cloud SQL 또는 원격 Postgres `REMOTE_DB_*`)을 사용하고 Flyway(`V1__init.sql`)로 스키마를 관리한다. 오디오 파일은 **Supabase Storage**(`takes` 비공개 버킷, 기본 한도 200MB) 및 사용자 Google Drive(P6)에 저장한다 | 확정 (2026-10-30 저장소 Supabase로 결정) |
| **KC-D4** | 복잡한 비즈니스 로직(1분 미만 연습 시간 보류 `keep`, 노션 Pull 루프 방지, 200MB 쿼터 잠금, 키 형식 정규식 검증)은 DB 저장 프로시저 대신 **Kotlin 서비스 트랜잭션 + 표준 SQL**로 구현하고 Kotest/JUnit으로 검증한다 | 확정 |
| **KC-D5** | 사용자별 노션 토큰·Gemini 키는 Ktor 서버에서 마스터 키(`APP_MASTER_KEY`, 32바이트 Base64) 기반 **AES-256-GCM**(12바이트 고유 IV)으로 암호화해 `integrations` 테이블에 저장한다. 어떤 API 응답에도 키 원문은 내려가지 않고 끝 4자리(`hint`)만 반환한다 | 확정 |
| **KC-D6** | Gemini 영상 분석은 `POST /api/v1/notes/analyze` 호출 시 `analysis_jobs`(`queued`)를 만들고 **Cloud Run Job `analyze`**(`runWithOverrides`, 제한 60분)에서 실행한다. 서비스 인스턴스 Coroutine은 응답 후 CPU 제한·인스턴스 종료로 멈추므로 쓰지 않는다. 70분 넘은 `running`은 cron이 `failed` 정리. 긴 영상도 분할 없이 분석하며, `guitar.py`·`keyboard.py`를 이식한 Kotlin SVG 렌더러로 지판/건반 다이어그램을 생성해 `notes.diagrams_svg`에 저장한다 | 확정 |
| **KC-D7** | 노션 실시간 동기화는 `sync_outbox` 테이블 + 사용자별 lease(`notion_sync.lease_until`, 획득·해제만 짧은 트랜잭션, 노션 호출은 트랜잭션 밖)로 처리한다. 저장 직후 비동기 즉시 실행(Fast-path, 보조)과 Cloud Scheduler 1분 주기 호출(`POST /internal/cron/notion-push`)을 병행한다 | 확정 |
| **KC-D8** | 사용자가 같은 키를 `guitar-practice` 앱과 공유할 수 있게 `integrations` PK를 `(user_id, app_id, provider)`로 둔다 | 확정 |
| **KC-D10** | **로그인은 Supabase Auth**(Google 공급자). Ktor는 JWKS로 access token 검증만, 자체 JWT·refresh 없음. `users.id` = JWT `sub`, 인증된 첫 요청에서 `users`·`profiles` 생성. 브라우저 세션 저장 키 `ulp:auth` | 확정 (2026-10-30) |
| **KC-D9** | **BYOK & 로컬 스토리지 보안 (X1 적용 완료):** 노션 실시간 연동과 Gemini 학습 노트는 각 키를 등록한 사용자 전용이다(`ulp:keys`에 끝 4자리·갱신 시각만 캐시). 모든 새 localStorage 키는 `ulp:` 접두어를 사용하며, XSS 정적 검사(`test/security.test.js`, 32개 테스트)와 CSP meta가 모든 HTML에 적용되어 있다 | 확정 |

- **명세 내용(필수 항목):** ① 만들거나 고칠 파일 목록(신규/수정) ② Kotlin 클래스·함수 시그니처 ③ DTO 필드 표(이름·타입·null 허용·DB 컬럼·예시) ④ 엔드포인트별 검증 규칙과 에러 표(조건 → `status`/`code`/`message`) ⑤ 처리 순서·트랜잭션 경계 ⑥ 테스트 케이스 표(이름/준비/요청/기대, 실패 케이스 포함) ⑦ 체크리스트(`[ ]` 항목마다 확인 명령과 기대 출력) ⑧ 금지 사항
- **명세 step 결과 파일:** `결과/<묶음>0_명세검토.md` — 앞 묶음 검토 결과(명세와 실제 구현 차이, 고칠 점), 이번 묶음에서 새로 정한 결정(메뉴얼 항목은 사용자 확인 기록).
- **관문 규칙 (구현 AI 필수):**
  1. 구현 step을 시작할 때 `개발산출물/명세/<step ID>_구현명세.md`가 없으면 **코드를 쓰지 않고 멈춘다.** 답변: `<step ID> 구현 명세가 없습니다. 다음 진행은 문서 보강 및 검토 후 진행이 필요합니다.`
  2. 명세 체크리스트를 모두 `[x]`로 채우지 못하면 완료 처리하지 않는다. 명세와 다르게 구현해야 하면 멈추고 묻거나, 결과 파일 "명세와 달라진 점"에 이유와 함께 적는다.
  3. 묶음의 **마지막 step**을 끝내면(PR CI 통과 후) 다음 묶음 step을 이어서 하지 않는다. 마지막 답변 끝과 7절에 아래 문구를 쓴다:
     `<묶음> 묶음(<step 목록>) 단계 완료하였습니다. 다음 진행은 문서 보강 및 검토 후 진행이 필요합니다.`
     다음 세션 시작 멘트는 `<다음 묶음>0` 명세 step(권장 effort 높음)으로 적는다.

## 4. 세션 진행 방법 (모든 step 공통)

1. `git checkout main && git pull` — 앞 step의 PR이 머지됐는지 확인한다(머지 안 됐으면 사용자에게 알리고 멈춘다).
2. 이 파일과 해당 step의 **입력 파일만** 읽는다. K1-1 이후 구현 step은 `개발산출물/명세/<step ID>_구현명세.md`도 읽는다(없으면 3.1절 관문 규칙 1에 따라 멈춘다).
3. 브랜치 `step/<step ID>` (예: `step/K0-1`)를 만들고 작업한다. 3개 이상 파일 변경·스키마/API 변경도 이 표에 승인된 범위 안이면 따로 묻지 않는다. 표 범위를 벗어나면 먼저 묻는다.
4. 완료 기준을 **실제로 실행해서** 확인하고, 출력(끝 몇 줄)을 결과 파일에 붙인다.
5. 결과 파일을 `개발산출물/결과/<step ID>_<이름>.md`에 쓴다. 다음 step에 필요한 값·결정·문서와 달라진 점을 모두 적는다.
6. 이 파일의 3절 상태 칸, 5절 결과 기록, 6절 겪은 문제, 7절 다음 세션 시작 지시를 고친다.
7. 커밋(`feat|fix|test|docs(scope): 요약`) → push → `main` 대상 PR → **CI 종료까지 대기(`gh pr checks --watch`)**.
   - 구현 step(주니어)은 PR 전에 `주니어_체크리스트.md`로 diff를 스스로 점검하고, CI가 통과하면 `PR #n — step/<ID> → main (CI 통과, 시니어 리뷰 대기)`로 알린다. 시니어 리뷰 코멘트를 반영하고 체크리스트에 항목을 추가한 뒤 아래처럼 알린다([협업\_시니어주니어.md](협업_시니어주니어.md) 7절).
   - CI 성공 시: `PR #n — step/<ID> → main (CI 통과, 머지하세요)`로 알린다(머지는 사용자가 한다).
   - CI 실패 시: 원인을 파악해 수정·push하고 CI가 통과할 때까지 해결한 뒤 알린다.
8. 마지막 답변 끝에 7절과 같은 다음 세션 시작 멘트(붙여 넣을 코드 블록)와 권장 effort를 적는다.

- **main CI 첫 실패(Pages `Not Found`):** Pages를 켜기 전에 돈 실행이었음. 켠 뒤 재실행으로 성공 확인(2026-10-30). 배포 단계는 그대로 둔다.
- **ruleset 필수 체크와 문서 PR:** 워크플로 `paths-ignore`로 건너뛰면 필수 체크가 '대기'로 남아 머지가 막힌다. 그래서 `changes` 작업이 작업 단위로 건너뛰고, 필수 체크는 항상 끝나는 `CI ok` 하나만 건다.

- **참고 코드 삭제 시점:** `apps-script/Code.gs`(노션 중계 원본)와 `scripts/*.py`(Gemini 분석 및 SVG 생성 원본)는 각각 `K4-2`와 `K5-1`에서 Kotlin 코드로 1:1 이식할 때 입력 파일로 참조한 뒤 `K4-3`, `K5-2` 단계에서 최종 삭제한다.
- **`gh` CLI 사용 시 주의:** 원격 저장소가 `origin`(`Hunseokc/ULevelP`)과 `upstream`(`Hunseokc/guitar-practice`) 두 개이므로 `gh` 명령 실행 시 반드시 `-R Hunseokc/ULevelP`를 붙인다.

- **Exposed 0.56.0 `slice` Deprecation:** `TakesTable.slice(sumExpr).where { ... }` 형태가 컴파일 오류를 유발하여 `TakesTable.select(sumExpr).where { ... }`로 교체하여 해결함.
- **Exposed `newSuspendedTransaction` 부모 Job 단절 및 코루틴 취소 시 커밋 문제:** `newSuspendedTransaction(Dispatchers.IO, db)` 형태로 디스패처 컨텍스트를 직접 넘기면 부모의 `Job` 컨텍스트가 상실되어 부모 코루틴 취소 신호가 트랜잭션으로 전파되지 않고 트랜잭션이 커밋되는 치명적인 문제가 발생함. `withContext(Dispatchers.IO) { newSuspendedTransaction(db = db) { currentCoroutineContext().ensureActive(); val res = block(); currentCoroutineContext().ensureActive(); res } }`로 개선하여 부모 Job 계층 구조를 보존하고 코루틴 취소 시 즉시 트랜잭션이 롤백되도록 해결함.
- **Node 22+ vm 샌드박스 객체 assert.deepEqual strict 프로토타입 불일치:** Node 22+ 내장 `node:assert/strict`의 `assert.deepEqual`은 서로 다른 `vm` 컨텍스트의 `Object.prototype`을 가진 객체 비교 시 내용이 일치해도 `Values have same structure but are not reference-equal` 오류가 발생함. 반환 객체를 `{ ...res }` 형태로 얕은 복사하여 비교하도록 수정하여 해결함.
- **브라우저 FormData Blob 멀티파트 파일 파트 분류 버그 (K1-3 M4):** 브라우저에서 `FormData.append('metadata', new Blob(...))` 시 웹 표준에 따라 `filename="blob"` 헤더가 자동으로 붙어 Ktor 서버의 `receiveMultipart()`가 이를 `PartData.FormItem`이 아닌 `PartData.FileItem`으로 분류함. 기존 서버 코드가 `FormItem`만 읽도록 되어 있어 metadata가 누락되는 버그가 발생함. `TakeRoutes.kt`의 `FileItem` 분기에서도 `part.name == "metadata"`일 때 스트림을 읽어 역직렬화하도록 보완하고 단위 테스트 T20으로 재발을 방지함.
- **Exposed 테이블 간 명시적 조인 외래키 누락 (K2-1):** `SessionsTable`과 `SongsTable` 간에 Exposed Table 정의 상 FK `.references()`가 선언되어 있지 않아 `SessionsTable innerJoin SongsTable` 호출 시 조인 컬럼 추론 오류가 발생함. `SessionsTable.innerJoin(SongsTable, { SessionsTable.songId }, { SongsTable.id })`로 명시적 조인 컬럼을 지정하여 해결함.
