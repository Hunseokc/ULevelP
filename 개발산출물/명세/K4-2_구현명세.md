### 2.3 `auth/CronOidcVerifier.kt` (package `ulevelp.auth`)

`docs/03-api-spec.md` 7.3절 규격에 따라 Google Cloud Scheduler의 OIDC ID 토큰을 검증한다.
- `SupabaseJwtVerifier.kt`는 수정하지 않고, `ulevelp.auth` 패키지의 public 클래스인 **`JwksProvider`, `HttpJwksProvider`, `StaticJwksProvider`, `JwksParser`를 그대로 재사용**한다.
- RS256 서명 검증은 `SupabaseJwtVerifier.kt:377`의 `RS256` 분기(`Signature.getInstance("SHA256withRSA")`)를 `CronOidcVerifier` 내부 `private fun verifyRsaSignature(publicKey: PublicKey, signingInput: ByteArray, signatureBytes: ByteArray): Boolean`으로 복사해 작성한다.
- 검증 실패 시 모든 분기에서 동일한 `UnauthorizedException("유효한 크론 OIDC 토큰이 아닙니다.")`를 던진다.

```kotlin
data class CronOidcConfig(
    val audience: String,
    val serviceAccountEmail: String,
    val jwksProvider: JwksProvider = HttpJwksProvider(URI("https://www.googleapis.com/oauth2/v3/certs")),
    val clock: Clock = Clock.systemUTC()
) {
    companion object {
        fun fromEnvOrNull(env: Map<String, String> = System.getenv()): CronOidcConfig? {
            val aud = env["CRON_AUDIENCE"]?.trim()?.takeIf { it.isNotEmpty() } ?: return null
            val email = env["CRON_SA_EMAIL"]?.trim()?.takeIf { it.isNotEmpty() } ?: return null
            return CronOidcConfig(audience = aud, serviceAccountEmail = email)
        }
    }
}

class CronOidcVerifier(private val config: CronOidcConfig) {
    /**
     * Authorization: Bearer <id_token> 검증:
     * 1. alg == "RS256", kid로 jwksProvider에서 공개키 조회 후 SHA256withRSA 서명 검증
     * 2. iss in setOf("https://accounts.google.com", "accounts.google.com")
     * 3. aud == config.audience
     * 4. email == config.serviceAccountEmail && email_verified == true
     * 5. exp > clock.instant().epochSecond
     * 하나라도 틀리면 UnauthorizedException("유효한 크론 OIDC 토큰이 아닙니다.") 발생
     */
    suspend fun verifyBearerHeader(authHeader: String?)
}
```

## 5. 처리 순서·트랜잭션 경계

### 5.1 `pushUserOutbox(userId)` (`docs/04-db-design.md` 3.4절 lease 패턴)
1. `integrationService.requireDecryptedNotion(userId, "ulevelp")`로 토큰과 `songsDb`, `sessionsDb`, `notesDb` 획득(없으면 `412 NO_KEY`).
2. **트랜잭션 1 (Lease 획득):**
   - `workerId = UUID.randomUUID().toString()`
   - `NotionSyncTable`에서 `userId eq userId`이고 `enabled eq true`이며 `(leaseUntil.isNull() or (leaseUntil less clock.instant().atOffset(ZoneOffset.UTC)))`인 행의 `leaseUntil = now + 5분`, `leaseOwner = workerId`로 UPDATE.
   - 갱신된 행 수가 `0`이면(비활성 상태이거나 다른 워커가 이미 실행 중) `PushResultDto(ok = true, processed = 0, failed = 0)` 반환.
3. **트랜잭션 2 (대기열 조회 및 정렬):**
   - `SyncOutboxTable`에서 `(userId eq userId) and (doneAt.isNull()) and (attempts less 5)`인 행을 조회한 뒤, 아래 **`outboxPriority(op, entity)` 오름차순 → `id` 오름차순**으로 정렬해 최대 20건(`BATCH_LIMIT_PER_USER`)을 선택한다:
     - `("upsert", "song") -> 1`, `("upsert", "session") -> 2`, `("upsert", "take") -> 3`, `("upsert", "note") -> 4`
     - `("delete", "take") -> 5`, `("delete", "session") -> 6`, `("delete", "song") -> 7`, `("delete", "note") -> 8`
4. **부모 링크 자동 보장 및 항목별 순차 처리 (노션 HTTP 호출은 반드시 DB 트랜잭션 밖에서!):**
   - **`session` `upsert` 시 부모 곡(`song`)의 `notion_links`가 없을 때:**
     - `SongsTable`에 해당 `songId`가 이미 삭제되어 없으면 이 `session` outbox 항목도 `done_at = now()`로 완료 처리(`processed++`)하고 넘어간다.
     - 곡이 존재하면 먼저 `pushSongUpsert(userId, songId, ...)`를 실행해 곡 노션 페이지와 `notion_links`를 만든 뒤 세션을 Push한다(곡 Push가 노션 오류로 실패하면 예외가 전파되어 해당 `session` outbox 항목도 `attempts + 1`, `failed++`로 기록됨).
   - **`take` `upsert` 시 부모 세션(`session`)의 `notion_links`가 없을 때:**
     - `SessionsTable`에 해당 `sessionId`가 없으면 `done_at = now()`로 완료 처리하고 넘어간다.
     - 세션이 존재하면 먼저 `pushSessionUpsert(userId, sessionId, ...)`(필요 시 상위 곡까지)를 실행해 세션 노션 페이지와 `notion_links`를 만든 뒤 녹음을 업로드한다(세션 Push가 실패하면 해당 `take` 항목도 `attempts + 1`, `failed++`로 기록됨).
   - 각 항목 처리 후:
     - 성공 시 짧은 트랜잭션으로 `SyncOutboxTable.update({ id eq item.id }) { it[doneAt] = now; it[lastError] = null }` 및 `NotionLinksTable` 갱신(`processed++`).
     - 실패 시 짧은 트랜잭션으로 `SyncOutboxTable.update({ id eq item.id }) { it[attempts] = attempts + 1; it[lastError] = errMsg.take(500) }` 및 `NotionSyncTable.update({ userId eq userId }) { it[lastError] = errMsg.take(500) }` (`failed++`).
     - 항목 처리 직후 짧은 트랜잭션으로 `leaseUntil = now + 5분` 연장.
5. **트랜잭션 3 (Lease 해제):**
   - `NotionSyncTable.update({ (NotionSyncTable.userId eq userId) and (NotionSyncTable.leaseOwner eq workerId) }) { it[leaseUntil] = null; it[leaseOwner] = null; it[lastPushAt] = now; if (failed == 0 && processed > 0) it[lastError] = null }`.

### 5.2 `runCronBatch()` (`POST /internal/cron/notion-push`)
1. **사용자별 Outbox Push (사용자 단위 예외 격리):**
   - `SyncOutboxTable`과 `NotionSyncTable`을 명시적 조인(`SyncOutboxTable.innerJoin(NotionSyncTable, { SyncOutboxTable.userId }, { NotionSyncTable.userId })`)하여 `enabled = true`이고 `doneAt == null && attempts < 5`인 고유 `userId` 목록(최대 20명) 조회.
   - 각 `uid`에 대해 `try { val r = pushUserOutbox(uid); pushedUsers++; processedOutbox += r.processed } catch (e: CancellationException) { throw e } catch (e: Exception) { NotionSyncTable에 lastError = e.message?.take(500) 기록 }`으로 감싸, 한 사용자가 `NO_KEY`·`CRYPTO_UNAVAILABLE` 등으로 실패해도 다른 사용자 및 2·3번 정리가 중단되지 않게 한다.
2. **`storage_trash` 정리 및 건수 집계 (`StorageTrashService.kt` 수정 없음):**
   - `StorageTrashTable`에서 `attempts < 5`인 `id` 목록(최대 50건) 조회.
   - `ids`가 비어 있지 않으면 `storageTrashService.purge(ids)` 호출 후, `StorageTrashTable.select(StorageTrashTable.id).where { StorageTrashTable.id inList ids }.count()`로 남은 행 수(`remaining`)를 세어 `purgedTrash = ids.size - remaining.toInt()`로 계산한다.
3. **멈춘 `analysis_jobs` 타임아웃 정리:**
   - `AnalysisJobsTable`에서 `status == "running"`이고 `startedAt < now - 70분`인 행을 `status = "failed"`, `error = "timeout"`, `finishedAt = now`로 UPDATE (`timedOutJobs`).
