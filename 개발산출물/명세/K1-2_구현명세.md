## 2. 시그니처

### 2.1 `storage/StorageClient.kt` (package `ulevelp.storage`)

```kotlin
class StorageException(message: String, cause: Throwable? = null) : RuntimeException(message, cause)

interface StorageClient {
    /** 실패하면 StorageException */
    suspend fun upload(key: String, bytes: ByteArray, contentType: String)
    /** 브라우저가 바로 열 수 있는 전체 URL. 실패하면 StorageException */
    suspend fun createSignedUrl(key: String, expiresInSec: Int): String
    /** 없는 파일도 성공으로 본다. 실패하면 StorageException */
    suspend fun delete(key: String)
}
```

### 2.2 `storage/SupabaseStorageClient.kt`

```kotlin
class SupabaseStorageClient(
    private val supabaseUrl: String,          // "https://<ref>.supabase.co" (끝 "/" 없음)
    private val secretKey: String,
    private val bucket: String = "takes",
    private val requestTimeout: Duration = Duration.ofSeconds(60),
    private val httpClient: HttpClient = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(5)).build()
) : StorageClient {
    companion object {
        /** SUPABASE_URL(trim, 끝 "/" 제거)과 SUPABASE_SECRET_KEY(trim)가 둘 다 비어 있지 않을 때만 만든다 */
        fun fromEnvOrNull(env: Map<String, String> = System.getenv()): SupabaseStorageClient?
    }
}
```

| 동작 | 메서드·URL | 헤더 | 본문 | 성공 |
| --- | --- | --- | --- | --- |
| `upload` | `POST {supabaseUrl}/storage/v1/object/{bucket}/{key}` | `Authorization: Bearer {secretKey}`, `apikey: {secretKey}`, `Content-Type: {contentType}`, `x-upsert: false` | 파일 바이트 | 2xx |
| `createSignedUrl` | `POST {supabaseUrl}/storage/v1/object/sign/{bucket}/{key}` | 인증 2개 + `Content-Type: application/json` | `{"expiresIn":<expiresInSec>}` | 2xx이고 응답 JSON의 `signedURL`(문자열) → 반환 `"{supabaseUrl}/storage/v1" + signedURL` |
| `delete` | `DELETE {supabaseUrl}/storage/v1/object/{bucket}` (`HttpRequest.Builder.method("DELETE", BodyPublishers.ofString(json))`) | 인증 2개 + `Content-Type: application/json` | `{"prefixes":["<key>"]}` | 2xx |

- 모든 호출은 `withContext(Dispatchers.IO)` 안에서, `HttpRequest.timeout(requestTimeout)`.
- 비 2xx → `StorageException("Supabase Storage <upload|sign|delete> 실패: HTTP <status>")`. 응답 본문 앞 200자는 `warn` 로그에만 남긴다(예외 메시지에 넣지 않음).
- `IOException`·`HttpTimeoutException`·`signedURL` 없음 → `StorageException(…, cause)`. `CancellationException`은 다시 던진다.
- `key`는 서버가 만든 `{uuid}/{uuid}.{ext}`뿐이라 URL 인코딩하지 않는다.

### 2.3 `service/TakeService.kt` (package `ulevelp.service`)

### 2.4 `service/StorageTrashService.kt`

```kotlin
class StorageTrashService(private val db: Database?, private val storageClient: StorageClient?) {
    /** 커밋된 storage_trash 행을 바로 지운다. 예외를 밖으로 던지지 않는다(CancellationException 제외). */
```

- `ids`가 비었거나 `db`·`storageClient`가 null이면 아무것도 안 한다.
- id마다: (트랜잭션) 키 읽기(없으면 다음) → (트랜잭션 밖) `storageClient.delete(key)` → 성공: (트랜잭션) 행 삭제 / 실패(`StorageException`): (트랜잭션) `attempts = attempts + 1`, `last_error = 메시지 앞 500자` + `warn` 로그.

### 2.5 `api/JsonInput.kt` 추가분 (K1-1 헬퍼와 같은 메시지 규칙)

```kotlin
fun JsonObject.requireInt(name: String, min: Int, max: Int): Int
fun JsonObject.requireInstant(name: String): OffsetDateTime   // UTC로 맞춰 반환
```
- `requireInt`: 없음·null → 필요 메시지, 형식은 `optInt`와 같음.
- `requireInstant`: 문자열이 아니거나 `OffsetDateTime.parse` → 실패 시 `Instant.parse` 둘 다 실패하면 형식 메시지(`ProfileService.parseIsoTimestamp`처럼). `2000-01-01T00:00:00Z` 미만 또는 `지금 + 1일` 초과 → `"$name은(는) 2000-01-01부터 내일(UTC)까지만 쓸 수 있습니다."`.

### 2.7 `POST /api/v1/takes` 요청 읽기 (라우트에서, 이 순서로)

1. `takeService.isStorageConfigured`가 false → 503 `STORAGE_UNAVAILABLE` (본문 읽기 전).
2. `call.request.isMultipart()`가 false → 400 `multipart/form-data 요청이 필요합니다.`
3. `Content-Length` 헤더가 있고 `> MAX_REQUEST_BYTES` → 413 `TAKE_TOO_LARGE` (본문 읽기 전).
4. `call.receiveMultipart(formFieldLimit = MAX_REQUEST_BYTES).forEachPart { part -> … ; part.dispose() }`:
   - `PartData.FormItem`이고 `name == "metadata"` → `part.value`를 문자열로 보관.
   - `PartData.FileItem`이고 `name == "file"` → `part.provider().readRemaining(MAX_FILE_BYTES + 1).readByteArray()` (`import io.ktor.utils.io.readRemaining`, `import kotlinx.io.readByteArray`).
   - 그 밖의 파트는 버린다.
   - 이 블록에서 난 `ApiException`·`CancellationException`은 그대로 다시 던지고, 그 밖의 예외는 400 `multipart 본문을 읽지 못했습니다.`
5. metadata 없음 → 400 `metadata 파트가 필요합니다.` / file 없음 → 400 `file 파트가 필요합니다.`
6. 파일 크기 `> MAX_FILE_BYTES` → 413 `TAKE_TOO_LARGE` / `== 0` → 400 `녹음 파일이 비어 있습니다.`
7. metadata를 `Json.parseToJsonElement` → `JsonObject`가 아니거나 파싱 실패 → 400 `metadata는 JSON 객체여야 합니다.` → 3.2절 표대로 검증 → `TakeUploadInput`.

## 5. 처리 순서·트랜잭션 경계

### 5.1 `upload(userId, input)` (04 3.2절)
1. **트랜잭션 A (읽기만):** `SongsTable`에서 `(id = songId, userId)` 없으면 404. `profiles.take_quota_bytes`와 `takes(userId, storage='supabase')`의 `size_bytes` 합계(`ProfileService.loadMeInTransaction`의 합계 쿼리처럼) → `used + bytes.size > quota`면 413 `TAKE_QUOTA_EXCEEDED`(업로드 전).
2. **트랜잭션 밖:** `takeId = UUID.randomUUID()`, `key = "$userId/$takeId.${MIME_EXT[mime]}"`, `storageClient.upload(key, bytes, mime)`. `StorageException` → 502 `STORAGE_ERROR`(DB 변경 없음).
3. **트랜잭션 B:**
   1. 곡 소유 재확인(없으면 404).
   2. `ProfilesTable.select(takeQuotaBytes).where { id eq userId }.forUpdate(ForUpdateOption.ForUpdate).single()` → 합계 다시 → 넘으면 413 `TAKE_QUOTA_EXCEEDED`.
   3. `ensureSession`(private): `(userId, songId, date)` 세션이 있으면 그 id(`created=false`). 없으면 `SessionsTable.insertIgnore { id = UUID.randomUUID(), userId, songId, date, seconds = 0, loops = 0, rate, a, b }` → `insertedCount == 1`이면 `created=true`, 0이면 다시 읽어 `created=false`. **이미 있던 세션의 값은 바꾸지 않는다.**
   4. `TakesTable.insert { id = takeId, userId, sessionId, songId, recordedAt, a, b, rate, durationSec, mime, sizeBytes = bytes.size.toLong(), storage = "supabase", storageKey = key }`.
   5. `created`면 `OutboxRepository.enqueueIfSyncEnabled(userId, "session", sessionId, "upsert")`, 그다음 `enqueueIfSyncEnabled(userId, "take", takeId, "upsert")` (이 순서).
   6. `TakeDto` 반환.
4. **3번이 예외로 끝나면:** `storageClient.delete(key)` 시도 → 그것도 `StorageException`이면 새 트랜잭션으로 `StorageTrashTable.insert { storageKey = key }` + `warn` 로그 → **원래 예외를 다시 던진다**(413이면 413 응답).

### 5.2 `signedUrl(userId, takeId)`
1. 저장소 미설정 → 503.
2. 트랜잭션: `(id = takeId, userId)` 녹음의 `storage`, `storageKey` → 없으면 404, `drive`면 400.
3. 트랜잭션 밖: `storageClient.createSignedUrl(key, SIGNED_URL_TTL_SEC)` → 실패 502.
4. `SignedUrlResponse(url, 3600)`.

### 5.3 `delete(userId, takeId)` (04 3.2.1절)
1. 트랜잭션: `(id, userId)` 녹음 없으면 404 → `storage = 'supabase'`면 `StorageTrashTable.insert { storageKey } get StorageTrashTable.id` → `enqueueIfSyncEnabled(userId, "take", takeId, "delete")` → `TakesTable.deleteWhere { (id eq takeId) and (userId eq userId) }` → id 목록 반환. (세션은 남긴다)
2. 라우트: `storageTrashService.purge(ids)` → `{ "ok": true }`. 저장소 미설정이어도 1번은 실행된다(행은 trash에 남음).

## 9. 금지 사항

- 스토리지 HTTP 호출을 DB 트랜잭션(`dbQuery { }`) 안에서 하지 않는다.
- 쿼터 재검사를 `FOR UPDATE` 없이 하지 않는다. 사전 검사만으로 끝내지 않는다.
- 업로드 뒤 DB 실패 시 파일을 남겨 두지 않는다(삭제 → 실패하면 `storage_trash`).
- 클라이언트가 보낸 `sizeBytes`·`storageKey`를 믿지 않는다.
- `SUPABASE_SECRET_KEY`를 로그·응답·예외 메시지에 넣지 않는다.
- 로컬 파일 저장 구현체, Drive JSON 등록, `migrate-drive`, cron 엔드포인트를 만들지 않는다(A0 결정).
- `catch`에서 예외를 삼키지 않는다. 예외를 밖으로 안 던지는 곳은 `StorageTrashService.purge`(행에 기록 + 로그)와 5.1-4번 정리 단계(원래 예외를 다시 던짐)뿐이다.
- K1-3을 이어서 하지 않는다.
